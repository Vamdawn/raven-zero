# 客户端形态与 Agent 连通方式

本文保留客户端形态的讨论过程。方案 A、HTTP 通信、JSON 任务定义与本地人工等待策略均已确认；完整规格见 [v1 规格](v1-spec.md)。

## 最新确认

用户已确认开启一次接单入口后自动执行，每任务使用专用会话并保留 Agent 原生交互，排除 Agent 调用框架方案，见 [ADR 0008](../adr/0008-framework-controlled-dedicated-sessions.md)。本文下方保留此前候选方案的分析；Agent 托管桥接与仅远端任务工具方案不再属于候选。

方案 A 已确认：用户显式启动持续接单管理程序，原生界面按需附着，工作阶段结束后自动收尾；不安装系统常驻服务。决策见 [ADR 0009](../adr/0009-client-manager-independent-ui.md)，比较依据见 [接单管理与前台串行执行](client-control-lifetimes.md)。

## 问题拆分

本地执行职责、承担职责的模块、模块的宿主与进程寿命是不同问题。客户端拥有工作区初始化、Agent 工作衔接、检查、可选交付、执行记录与结果上报等职责，不因此必然需要另一个独立常驻产品进程。

术语表中的“客户端调用 Agent”描述了主动控制方向，该方向现已确认。此前分析的 Agent 托管方案采用相反调用方向，现已排除。

持续自动接任务需要有运行中的本地执行者，或由可靠宿主唤醒它。执行者可以是框架程序，也可以是支持任务触发的 Agent 宿主。没有运行中的程序和唤醒机制时，服务端只能排队等待。

## 候选形态

| 形态 | 控制方向 | 接新任务的条件 | 主要代价 |
| --- | --- | --- | --- |
| 独立控制程序 | 框架创建并观察专用 Agent 工作会话 | 用户启动程序，或系统托管程序持续运行 | 必须建立原生界面与同一会话的连接契约，管理后台会话与退出 |
| Agent 托管桥接 | 原生 Agent 调用框架工具，或宿主事件触发任务 | 用户触发，或目标宿主提供可信任务触发能力 | 工作区切换、任务完成与恢复受宿主能力约束；MCP 工具本身不保证自动触发 |
| 按需前台程序 | 用户启动一次执行，程序初始化工作区后衔接原生 Agent | 用户开始一次接单或执行 | 不运行时不能领取任务；仍要可靠观察和结束原生工作会话 |
| 仅远端任务工具与 Agent 指令 | Agent 自己执行本地命令并报告 | 原生 Agent 被用户或宿主触发 | 初始化、检查与交付顺序主要依赖 Agent 遵循指令，改变此前由确定性客户端组件执行交付的决定 |

上述候选现已收敛为方案 A，首版不同时实现其他运行形态。本地任务生命周期模块保留可嵌入能力。

## Agent 连通的两种方向

### 框架主动控制 Agent

框架准备任务工作区，再通过 Agent 的程序化接口建立专用工作会话。适配器使用结构化事件跟踪执行，原生界面必须连接同一个工作会话处理审批与问答。

复用一个已有 Agent daemon，不等于复用用户日常工作会话。任务工作区与任务执行实例应绑定到明确的会话身份，恢复不能根据“最新会话”猜测。

Codex 的 [app-server](https://learn.chatgpt.com/docs/app-server)提供程序化会话与审批协议、原生终端附着方式。尚无公开契约保证第三方程序创建的任务会进入已有 Codex App；目标版本仍需实际验证多客户端订阅和待答请求行为。

### Agent 调用框架

框架通过本地 MCP 工具或按需命令提供领取、准备、检查、交付与上报能力。用户在原生 Agent 中使用这些能力，权限与问答自然留在原生宿主。

本地 MCP helper 仍是本地执行进程，通常由 Agent 托管；这可以减少独立进程的安装和管理，但不能视为没有本地执行模块。[Claude 官方 MCP 文档](https://code.claude.com/docs/en/mcp)明确本地 stdio server 在用户机器上作为进程运行。

[MCP 工具调用](https://developers.openai.com/plugins/concepts/mcp-server)由模型选择工具并调用，不等同于任务到达时自动启动工作。宿主可以提供额外触发能力：例如 [Claude Channels](https://code.claude.com/docs/en/channels)可以向运行中的会话注入事件，但只有会话保持打开时才有事件，且不证明能自动创建新的隔离任务会话。

Codex [后台 Hook](https://learn.chatgpt.com/docs/hooks)完成时，若没有活动 turn，等待下一用户 turn，不自行启动新 turn。[OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)当前支持 Work Cloud 与 dots，不能据此保证本地 Codex 的自动接单能力。

## 两个不能隐藏的约束

### 工作区与会话授权

本地 helper 创建目录或改变自身工作目录，不等于原生 Agent 所有工具的工作目录、项目配置与授权范围随之改变。Agent 托管方案需要明确的会话迁移契约，或在目标工作区建立新会话。

不同宿主具有不同能力，例如 [Claude 权限文档](https://code.claude.com/docs/en/permissions)提供会话目录切换机制；不能把一种 Agent 的机制当作通用保证。

### 工作结束与交付门禁

一次 turn 结束、界面退出、任务声明完成，以及任务检查通过，是不同事件。原生界面仍然可以启动下一轮修改时，检查与交付可能面对不断变化的工作区。

进入最终交付前，需要明确的任务完成意图、Agent 当前操作结束，以及交付期间不会继续写入的约定。检查和交付针对同一份稳定工作区；完成声明仅请求进入检查阶段，不证明成功。若原生界面没有可靠输入暂停机制，可能需要先结束该任务工作会话再交付，此规则尚待讨论。

## 此前建议与已确认结论

不要把独立常驻客户端写成核心前提。优先把本地执行职责封装成可嵌入模块，将领取任务、准备工作区、执行检查与交付、恢复进度和上报结果的复杂性集中处理。

自动执行、每任务专用会话与原生界面按需附着均已确认，Agent 托管方案已排除。HTTP 长轮询、JSON 任务定义与本地人工等待策略均已确认。完整规格已确认，按用户要求暂不开始实现。
