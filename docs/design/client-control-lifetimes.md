# 接单管理与前台串行执行

客户端形态现已确认采用方案 A，见 [ADR 0009](../adr/0009-client-manager-independent-ui.md)。本文保留两种方案的比较依据。框架主动控制 Agent，用户开启一次接单入口后自动执行，每任务使用独立工作区和专用会话，人工交互留在 Agent 原生界面。

## 两者不是不同的控制架构

两者都需要本地执行模块完成初始化、Agent 工作衔接、检查、可选交付、进度记录与上报。区别是接单循环是否与当前原生终端界面耦合；系统常驻托管是另一个部署问题，不是本次两个方案的分界。

## 方案 A：持续管理程序，原生界面按需附着

用户启动管理入口，程序在其运行期间持续接单和观察任务，每个任务的原生界面独立打开或附着。程序可以是前台命令，不必安装系统 daemon。

```text
接单管理程序
  ├─ 任务执行实例 A → 工作区 A → Agent 会话 A ← 原生界面 A
  └─ 任务执行实例 B → 工作区 B → Agent 会话 B ← 原生界面 B
```

接单、检查、交付与结果上报不依赖原生界面是否打开。无界面时，能够自动执行的工作可以继续，遇到需要本地回答的请求则等待；用户需要准确的任务会话附着入口。界面关闭不等于任务停止或完成。

可设置一个或多个执行名额；多任务分别拥有工作区、会话与交互入口，不能共用一个未经隔离的输入通道。[v1 规格](v1-spec.md) 已确认默认一个名额、允许配置多个。

主要代价是执行状态与界面状态分开，需要核查同一会话的结构化观察、原生界面附着、待答请求送达与界面关闭后的行为。仅仅启动 app-server 不证明这些能力全部成立。

## 方案 B：一个前台入口，当前终端依次进入任务原生界面

用户启动一次前台入口，程序持续接单，每个任务依次占用当前终端；任务完成检查、交付和结果保存后，程序自动进入下一任务，无须用户逐任务重新启动命令。

```text
开启接单
  → 领取任务 A、初始化工作区 A
  → 当前终端进入 Agent 会话 A 的原生界面
  → 结束工作阶段、检查、交付、保存并上报
  → 领取任务 B、进入 Agent 会话 B
  → 持续循环
```

用户直接看到当前任务，问答与审批容易定位，默认一个执行名额的形态直观。并行工作流仍可由多台客户端机器分别执行；它不意味着单个终端可以同时提供多个原生交互会话。

主要代价是原生界面必须在工作阶段结束后可靠交还终端，否则程序不能自动进入下一任务。如果需要用户每次手动关闭界面才能继续，就不满足当前确认的连续自动执行体验。目标 Agent 的界面退场、任务停止与进程归属契约必须验证。

## 对比

| 方面 | A：管理程序与原生界面分开 | B：当前终端依次进入原生界面 |
| --- | --- | --- |
| 连续接单 | 管理程序存活期间持续接单 | 前台入口运行期间持续接单 |
| 同客户端并发 | 可通过多个执行名额和独立界面实现 | 首版自然串行；并行需要额外界面安排 |
| 人工交互 | 按需附着对应任务会话，未附着时请求等待 | 当前任务原生界面直接呈现 |
| 原生界面关闭 | 管理程序继续核查任务状态 | 必须回到管理循环并核查，不能以关闭推定成功 |
| 下一任务启动 | 不依赖上一任务界面的退场 | 依赖上一任务交还当前终端 |
| 嵌入其他项目 | 接单与执行模块易由既有应用托管 | 执行模块可复用，但前台终端安排不适合所有宿主 |
| 本地管理入口退出 | 需明确停止接单、等待或停止已有任务 | 同样需要退出规则，终端关闭可能同时影响多个进程 |

## 两者共同的完成、退出与恢复规则

- Agent 一轮正常结束只提供进入检查阶段的候选信号，不直接证明任务成功；纯自然语言问答、多轮修改与最终工作结束需要明确区分。
- 检查与交付前结束本次工作阶段，将本版成果发布到受保护的独立交付工作区；同一任务的后续写入不能修改这份成果。原工作区是否仍有后台写入与交付隔离分开核对，见 [ADR 0020](../adr/0020-protected-delivery-workspace.md)。
- 任务成功依赖任务声明的交付前检查、可选交付和交付后检查。检查失败按既定任务失败规则处理，不擅自增加无限 AI 修复循环。
- 本地结果先持久保存，再上报；本地完成与服务端确认收到结果是不同事实。结果确认丢失不能导致重新执行任务或重新生成 Git 提交。
- 网络断开时，本地执行程序仍运行则继续工作，重连补报；本地程序退出与机器断网是不同情况。
- 原生界面退出不是 Agent 已停止的证明；恢复必须根据已保存会话身份核对实际状态。
- 管理程序重启可以补报结果，但不隐式重跑 Agent；继续或重试遵守用户显式选择。
- 停止接单并等待已有任务，与请求立即停止执行，应有不同的入口。等待人工回答可能使前者长期等待；实际停止仍需确认。

## Codex 验证要求

[官方 app-server 文档](https://learn.chatgpt.com/docs/app-server)提供结构化协议和原生终端附着方式。两种形态都要验证目标版本中的同会话观察、审批与问答行为、界面退出与后台执行的关系。方案 B 额外需要验证原生界面可靠交还终端；Codex App 接管第三方任务仍不能作为已保证能力。

## 已确认选择

采用方案 A：用户显式启动接单管理入口，原生界面按需附着，暂不安装系统常驻服务。它让接单与执行不依赖当前终端的退场，也更适合后续受控工作节点和嵌入其他项目。

未附着原生界面时，审批或问答保持等待，不自动批准。Agent 工作阶段结束后自动收尾，隔离该会话后续写入，再执行检查与交付；不保留自由多轮交互直至用户逐任务手动结束。继续修改通过显式恢复或后续任务处理。
